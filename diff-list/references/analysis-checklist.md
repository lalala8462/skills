# diff-list 分析检查清单

## 1. 最终净变化

先确认指定 Git 修订形成的最终代码结果：

- 方法新增、删除、修改；
- 字段、类型、默认值、注解与 Java 类级初始化块变化；
- SQL/Mapper 变化，以及无法由现有解析规则展开的 XML 文件变化；
- 配置文件变化；
- 多次修改同一位置、修改后撤销，以及提交说明与最终实现是否一致。

中间提交只用于解释演进和风险，最终结论以结果树为准。最终没有净变化时应明确记录，不虚构改动或测试用例。

## 2. 一层直接影响

向上检查变化方法的直接调用方，向下检查直接被调用方和外部出口。

重点：

- DB/Mapper；
- HTTP/RPC/MQ；
- 外部系统调用及请求；
- 状态、关键字段与数值；
- 配置直接消费者；
- 参数来源；
- 最终响应和异常。

## 3. 字段与接口契约

字段变化时核对：

- 请求/响应 DTO；
- JSON/XML/RPC/MQ 字段；
- 数据库列、resultMap、SELECT/INSERT/UPDATE；
- 直接消费者；
- 历史数据和已有调用方的可验证影响。

## 4. 配置

核对：

- 配置键、作用域、默认值；
- 读取位置；
- 条件/guard；
- 直接使用点；
- 配置文件实际变化；
- 变更方法及其直接关联流程依赖的数据库配置，包括分支开关和实际使用的既有地址、渠道等；结合读取位置、条件和使用位置判断关联，不以名称猜测；
- 配置键在基线和结果快照中的状态，以及 Mapper、实体映射或明确 SQL 对表名和列名的支持；无法核实的内容标记待确认；
- 配置加载和缓存路径是否影响测试前提，能确认差异时在报告中说明；不推断目标环境的配置记录。

有源码依据的配置前提写入报告的表配置 DML 准备清单，即使提交未包含 DML 脚本。表格格式与状态定义见[报告契约](analysis-contract.md#表配置-dml-准备清单)。

## 5. 高价值风险

优先关注：

- 状态转换；
- 数值计算与精度；
- 幂等和重复请求；
- 参数来源变化；
- 配置切换及初始化逻辑的生效时机；
- 未能自动展开的 XML 业务配置变化；
- 数据库及外部系统副作用；
- 接口契约，包括查询字段或字段别名变化对外部排序参数的影响；
- 异常恢复和边界条件。

branch、switch、contains、集合数量等源码事实由 Agent 结合业务变化形成测试场景。脚本不从这些事实直接生成正式业务测试结论。

当某个字段、方法、配置键、Mapper 或 review unit 需要深查时，优先使用 `review_query.py` 展开其完整 fact/relation/evidence，减少手工在多个材料间跳转。查询结果只是索引，不代表未命中材料无关。

## 6. 测试用例

每条用例：

- 只描述一个明确业务目的；
- 写清配置和数据前提；
- 步骤可执行；
- 结果可观察；
- 每个 `review_unit_id` 必须有 `unit_assertions` 绑定直接主事实与可观察断言；脚本只展开所引用事实的证据。

正常逻辑已在需求验收中覆盖时，不在回归或边界 sheet 重复。

`coverage.json` 的 `pending_review` 只用于发现尚未绑定测试场景的 review unit。优先查看 `candidate_case_ids` 判断现有场景是否已经实际覆盖；能覆盖则补充 unit 与主事实—断言绑定，不能覆盖才新增用例。新增用例以实际业务风险和测试价值为依据，已覆盖的单元使用现有用例建立引用。

## 7. 报告

第 4 章写清既有功能影响：受影响流程、触发条件、原因和可观察后果。正文不罗列 fact/evidence 机器编号，完整来源保留在结构化文件。

第 6 章严格区分：

- 静态源码分析；
- 构建/自动化测试；
- 数据库验证；
- 真实外部系统或环境联调。
