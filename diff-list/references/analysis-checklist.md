# diff-list 分析检查清单（内部）

## 使用原则

默认只围绕 **最终净变化 + 一层直接影响** 复核。脚本已经确定的 AST、调用、配置、Mapper 和证据直接使用；AI 不再为了完整链路重复全仓搜索。

检查顺序：

1. 本次最终代码究竟改变了什么；
2. 变化点直接调用谁、谁直接调用变化点；
3. 是否直接影响 DB/Mapper、HTTP/RPC/MQ、渠道、配置、状态、金额、单号或最终响应；
4. 对这些已确认变化编写可执行测试用例。

关键词、提交说明、同名字段和语法候选只能辅助理解，不能扩大默认范围。

## 提交意图

- 最终行为以指定修订的结果树为准。
- 提交说明只用于解释目标和发现“说明与最终实现不一致”。
- 同一方法反复修改、先增后删或最终净差异为零时，仅在与最终业务风险相关时补充说明。
- 不按每个提交重新分析整条调用链。

## 一层直接影响

向上只看变化方法的直接调用方；向下只看变化方法直接调用的方法/外部出口。

重点检查：

- DB/Mapper 的读写及动态 SQL；
- HTTP、Dubbo/RPC、MQ、渠道调用；
- 状态、金额、交易号/退款号/外部订单号；
- 配置项及直接消费者；
- 最终返回和明确异常；
- 参数来源变化。

达到一层后停止。没有直接证据时，不继续通过同名字段、返回类型、字符串关键词或远距离调用猜测关联。

## 字段和契约变化

字段新增、删除、类型/默认值/别名变化时，核对：

- 请求/响应 DTO、JSON/XML、RPC/MQ 报文；
- 数据库列、Mapper/resultMap/SQL 列；
- 直接读取或写入该字段的方法；
- 旧调用方或历史数据是否存在明确的一层兼容性影响。

不能从实体字段变化直接推断 DDL，也不能因为未找到直接消费者就声称“无影响”。

## 配置

配置变化核对：

- 键、作用域、默认值和取值语义；
- 当前变化范围内的直接读取位置和使用条件；
- 新旧键是否仍被直接消费；
- 配置文件新增/修改/删除是否与代码行为一致。

不为了寻找所有潜在消费者重复执行全仓搜索；一层之外只说明静态分析边界。

## 高价值风险

优先保留会改变以下结果的场景：

| 风险 | 重点结果 |
| --- | --- |
| 状态转换 | 状态不非法逆转，通知/落库一致 |
| 金额与精度 | 金额、单位、舍入结果可判定 |
| 幂等/重复请求 | 执行次数、流水号、退款号可核实 |
| 参数来源 | 下游实际使用正确来源 |
| 配置切换 | 不同配置值对应行为明确 |
| DB/渠道副作用 | 写入内容、调用参数、调用次数明确 |
| 接口契约 | 新旧请求/响应直接消费者可验证 |
| 异常与边界 | 明确错误结果或不会产生错误副作用 |

branch、switch、contains、集合数量只是形成测试场景的源码依据，不要求脚本为每个结构自动生成多个 obligation。

## 用例

默认直接编写 `schema_version=3` 的 `test-cases.json`。

每条用例必须：

- 只覆盖一个明确业务目的；
- 写清配置和数据前提；
- 步骤可直接执行；
- 至少有一个接口、页面、日志、数据库、文件或下游行为的可观察结果；
- 源码事实型用例只引用本条真正依赖的 fact/evidence。

四类唯一归属：需求验收 > 既有核心流程回归 > 关联回归 > 业务规则与边界验证。正常逻辑已经在重点场景覆盖时不要重复。

旧 `test-point-contract.md` 仅用于 schema_version=2 兼容流程，默认分析不要使用。

## 报告

- 写最终生效行为，不复制大段源码和内部 ID；
- 第 4 章只保留真正的特殊逻辑、兼容性和既有功能影响；
- 第 5 章只列 Excel 文件名及四类数量；
- 第 6 章明确静态分析、构建/自动化测试、数据库和真实渠道联调哪些实际执行过；
- 一层之外未展开的内容写成分析边界，不写成“无影响”或“已验证”。
