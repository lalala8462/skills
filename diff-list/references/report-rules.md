# diff-list 报告填写规则（仅按需读取）

## 四类改动清单

**需求改动**：以业务触发条件、处理结果、跨项目职责和影响范围描述，避免仅翻译类名。

**表字段 DDL**：只记录已核实的表/字段/索引结构变化，列改动前后定义及相关 NULL/默认值、仓库相对 DDL 脚本路径与修订。代码要求新字段但无脚本时写“代码涉及新增字段，DDL 脚本未找到”。复用既有字段和 Redis key 不算 DDL；无变化写“无”。

**表配置 DML 准备**：描述测试前必须具备的配置事实，不代替环境决定 INSERT 或 UPDATE。列“系统/表、字段（配置键）、字段状态、配置含义/取值、作用范围和测试前提”；字段状态只针对**该系统/表/作用域中的配置键**，新增支持用“新增”，沿用旧配置用“已存在”，与物理列状态、环境实际记录无关。同键跨表或作用域状态不同必须分行；废弃、删除或含义变化另行说明，不暗示必须清理记录。不要使用“是否必须新增数据”列或“已有数据则无需新增”。区分仓库交付 DML 脚本与环境需要配置，逐服务核实映射枚举和配置生效分支，敏感值不输出。

“字段状态”由源码复核后填写，候选脚本或格式校验不代替判定。必须比较本次分析基线与最终修订中**同一系统、作用域、配置键及取值含义**的支持情况：

- 本次首次支持的配置键标“新增”，即使承载它的配置表、物理列早已存在，或其他系统已有同名键。
- 已有配置键本次新增支持某个取值或用途时，将新增部分单独列行为“新增”，并在配置含义中说明是新增取值或用途；不能把整个键笼统标为“已存在”。旧取值仍需准备时另列为“已存在”。
- 只有基线已经支持相同作用域、键、取值和用途，且本次继续沿用，才标“已存在”。当前源码出现该键、环境可能已有记录、或者配置此次首次写进报告，都不足以单独决定状态。
- 仅修改默认值或已有取值语义时说明前后变化，不包装为新增配置。基线支持情况无法核实时继续追踪，不能默认填写“已存在”。

“字段或配置键”列使用已核实的物理字段名和代码配置键，不以中文注释、用途或描述代替；中文说明放在“配置含义/取值”列。例如 `param_name`、`param_value`（`WEBAPI_CODE_BASE_URL`）。仅确认配置键而未确认物理字段时只填写已确认的配置键，不猜测表或字段；两者都无法确认时继续追踪，关键配置无法确定时向用户说明并询问，不编造清单。

分别写清关键路由值的来源、用途和服务作用域，避免混用渠道、交易类型、商户类型或接口类型。已核实配置表及字段时具体列出；无法证实时仅列已确认的系统、作用域、配置项及用途，不猜测物理落点或暗示已查询环境记录。

**配置文件**：环境 properties 改动统一称 `profile/*.properties 配置文件`；实际使用 YAML/XML 等则如实描述。标记新增、修改、删除、废弃及沿用的键、用途、代码默认值或取值限制、覆盖优先级与环境差异，代码引用新键但找不到配置时说明缺失。发生配置文件变化时附实际格式的相关代码块，真实密钥用占位符；无变化写“无”。

## 业务与测试

业务流程按输入、校验、路由、渠道交互、保存状态、通知和失败恢复叙述。Mermaid 8.8.3 使用 `flowchart TD` 或 `sequenceDiagram`，不要把失败画成成功。

特殊逻辑额外核对**提交说明与最终实现的差异**，以及同一业务点的反复修改、前后相反或撤销：按提交先后核实实际变更和最终行为；说明不等于需求结论，文件级重复/文本反向信号不是业务冲突的证明。真正存在与最终业务相关的分歧或回归风险时在第 4 章说明最终状态、影响面及为何额外关注；对应测试只在 Excel 的最终所属类别展示。**净差异为零时仍检查提交历史，但不得把已撤销变化描述为最终生效功能。**

特殊逻辑只描述与本次变化相关的条件、例外、被注释而未启用的调用、延迟与重复请求、订单号复用、并发锁、超时边界、未知状态、幂等和回补；协议限制仅在核实后给出。注释与实际代码冲突按可执行逻辑说明。**第 4 章必须明确“既有功能影响”**：哪些旧接口、调用方、历史数据、旧代码版本或既有支付/退款/查询/对账/通知链路可能因本次改动产生可验证变化；给出触发条件、原因和实际或预期影响，并区分已核实事实与测试风险，不凭候选缺失断言兼容。

用例统一在单独 Excel 输出，按 **需求验收、既有核心流程回归、关联回归、业务规则与边界验证** 分四个工作表。先按 [测试点契约](test-point-contract.md) 编译结构化测试点，模型再编写步骤；相同测试点按上述顺序唯一归属，不按风险高低或用例措辞归类。需求验收包含必要边界与反向规则；核心及关联回归必须有本次影响依据，不铺开通用全量回归。

每条仍使用五列“用例编号、用例名称、前置条件、步骤描述、预期结果”；步骤必须可直接执行。**“可观察证据”是预期结果的必备质量标准**：每条至少写明一个真实可检查的渠道、具体对象/字段及可判定的值、状态、条数、次数、存在性或其他条件，不能只写“处理成功”“符合预期”“状态正确”。`observable_evidence` 保留 surface/target/assertion 并增加与测试点一致的 constraint；导出器补入固定触发条件、全部数据组和结构断言，不增加列。脚本不证明额外自然语言步骤、业务真实性或观察渠道可获取性。

去重由入口、结构规则、规范条件、观察对象及断言类型确定；实例替换仅合并数据组，预期冲突报错。仅有标题或文字相似不合并；没有显式等价依据的不同条件保守保留。一个用例可承载同一目的、相同准备及操作下的多个不同断言，但测试点不能重复承载，合并前覆盖要求不能丢失。仅列本次影响范围内的可验证场景，不凑数量。Markdown 第 5 章只列 Excel 文件名、四类数量和总数，不重复用例内容。只接受当前四类用例格式。

当不同字段可能被误用，或涉及单位转换、状态映射和多记录匹配时，优先用可区分来源的具体示例及确定预期；例如输入金额字段使用不同数值并标注单位，或给每条记录不同标识。示例仅用于验证，不冒充已执行结果或真实业务数据；预期以核实的代码和已确认业务需求为依据。

## 文档与验证

标准流程交付前运行分析覆盖校验，并将同一组 analysis/review/cases 参数传入 Excel 导出和报告校验。证据编号、覆盖关联及补查处置仅存内部材料；用户文档保持原模板与五列用例格式。内部格式检查不代替完整覆盖校验，静态边界补查不代表实际联调。

所有项目合并为一份差异报告及一份四类工作表 Excel。正文以指定修订中的**最终业务效果**为准；第 4 章可以补充与最终行为/回归风险相关的提交意图偏差或中途撤销线索，但须与最终生效逻辑明确区分。不展示源码行号、内部取证、绝对本地源码路径或未解决的问题。验证情况区分静态取证、构建测试和真实环境联调，不得把未执行的验证写成已完成。结构校验 PASS 不能替代 Mermaid 全语法校验、动态绑定和业务预期核实。
