# diff-list 报告规则

## 基本原则

报告以指定修订的最终业务效果为准。提交历史只用于解释与最终行为相关的演进、反复修改和风险。

事实、业务结论和测试预期分开：

- 源码事实来自当前 analysis；
- 业务含义由 AI 结合源码和用户提供的需求核实；
- 未实际执行的测试或联调不能写成已验证。

## 改动清单

### 需求改动

描述最终生效的接口、流程、字段、路由、状态和业务规则。

### DDL

只有能从明确 SQL、迁移脚本或已确认数据库契约证实时，才列具体表字段变化。

### DML

配置表或业务初始化数据只有在代码/脚本明确要求时列出；不要从代码停止读取某配置推导必须删除数据库行。

### 配置文件

写明新增、修改、删除的实际键、作用域、默认值和用途。配置片段使用真实格式，敏感值使用占位符。

## 业务流程

按输入、校验、路由、外部调用、落库、通知、失败处理描述。

Mermaid 使用 `flowchart TD` 或 `sequenceDiagram`。

## 特殊逻辑与既有功能影响

重点说明：

- 条件和例外；
- 状态、金额、单号来源；
- 幂等、并发、超时；
- 未知状态和补偿；
- 配置切换；
- 对已有接口、调用方、历史数据和既有流程的可验证影响；
- 提交说明与最终实现的明显偏差。

## 测试用例

固定四类：

1. 需求验收
2. 既有核心流程回归
3. 关联回归
4. 业务规则与边界验证

Excel 固定五列：

- 用例编号
- 用例名称
- 前置条件
- 步骤描述
- 预期结果

每条预期至少包含一个明确的可观察结果，例如接口字段、页面值、日志事件、数据库状态、文件内容或下游调用参数/次数。

同一场景只放入一个最主要的类别。

## 报告生成与校验

先生成 `test-cases.json`，再导出 Excel，然后生成 Markdown 候选。

最终校验核对：

- 项目/SHA；
- 报告章节；
- 四类用例数量；
- 快审范围；
- fact/evidence 引用；
- evidence 对应固定 Git 快照真实源码。

全部通过后使用 `validate_report.py --finalize` 定稿。

结构校验通过不代表业务测试或真实环境联调通过。
