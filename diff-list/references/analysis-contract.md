# 固定分析与覆盖契约

每次使用当前版本重新采集、分析并生成完整材料，不迁移或接受旧版分析数据。

本文件用于内部分析。源码位置、内部证据编号及未解析明细不复制到用户报告；报告验证情况如实说明静态边界。

## 输入与修订

单项目沿用 `--repo` 配合重复的 `--rev SHA[:parent]`，或完整 `--base/--head`；多项目使用 `--manifest`，不能混用。清单示例：

```json
{"projects":[
  {"name":"service-a","repo":"https://github.com/example/service-a","revisions":["FULL_SHA"]},
  {"name":"service-b","repo":"https://github.com/example/service-b","range":{"base":"BASE","head":"HEAD"}}
]}
```

项目名唯一；revisions 亦支持 `{"rev":"FULL_SHA","parent":2}`。统一入口每项目只创建一个分析 clone，后续读取固定树。离散提交的 result 是独立索引合成树，可能与最后选中提交的树不同；冲突不回退其他范围。跨项目合同匹配仅是源码约定推导，不证明服务发现、发布版本或实际部署绑定。

## 规则与限制

可选 JSON 规则包含 `version=1`、`config_annotations`、`config_scopes`、`aliases`、`relation_review_tokens`、`limits`。注解按短名识别，属于可配置约定而非框架类型绑定；不支持或歧义必须复核。`relation_review_tokens` 用于补充仓库中无法从通用类型名称识别的关键调用接收者、调用者或方法名，按精确、有区分度的值配置，不添加宽泛词以绕过范围筛选；参数文本不参与范围匹配。通用配置注解为 Value、ConfigurationProperties；自定义 ParamKey 和企业/商户作用域在 `rules/rhf.json`，必须显式选择。不根据类名中的 Ent/Mch 自动猜测作用域。

`limits` 的正整数键：`files=10000`、`file_bytes=1048576`、`total_bytes=134217728`（每快照），以及调用关系 `depth=2`、每快照 `methods=100`、`context_bytes=8388608`。自定义规则可以调低调用深度和方法数，不可超过 2 层和每侧 100 个方法。相同 blob 复用解析结果，但事实和证据分别绑定 baseline/result。达到扩展上限不创建预算边界或远距离缺口义务；受影响的变更 Java 文件无法索引、变更方法超过每侧方法上限或关键源码证据因容量不足而缺失时，写入 `hard_errors`，禁止将结果作为完整报告交付。

## 产物与关系状态

`analysis.json` 包含 schema_version、analyzer_version、analysis_id、rules、limits、projects 和 cross_project_relations。每个项目包含 repository、analysis_clone、snapshots、git、history、facts、relations、obligations、兼容字段 `boundaries`（当前版本为空）和 stats。未解析关系只保留关键业务结果相关项；`hard_errors` 非空或缺少快照禁止完成。

- source_resolved：按源码声明确定的目标，不保证运行时分派。
- convention_inferred：注解访问器、单一源码实现或跨项目合同匹配等约定推导。
- unresolved：重载歧义、多实现、外部依赖或接收类型不明，保留候选和停止原因。

同一方法中明确构造、传入未解析调用边界的对象，其非访问器覆盖方法可作为回调候选展开；例如回调继续提交 Runnable。此类关系始终是 convention_inferred，保留传递位置，不证明实际调度、调用次数或执行顺序。未构造的参数对象及无法关联的动态回调继续保留边界。

新增 `src/test` 方法及新增测试类的字段和类签名不作为变更起点或业务覆盖义务；测试目录不运行补充语法候选扫描。已修改或删除的既有测试方法仍可能进入主索引，均不能替代生产源码、协议或正式需求的证据。其他路径的测试代码未必能被自动识别，需人工区分。

同名字段候选只有在已进入调用链，或接收类型可解析且与变化处的接收类型一致时才扩展关联；其余保留在 `field_label_candidates`，包含固定快照侧、方法、文件、字段名和接收类型，作为按需检索的弱线索，不生成逐项复核义务，也不表示无影响或已经核查。根据实际调用、对象构造和映射关系判断是否需要补查；复杂别名、跨类型映射和动态消费仍须关注。同一调用链内跨方法写入同名字段且来源不同、接收对象绑定无法确认时，生成待复核风险候选，不认定为同一业务对象。覆盖校验通过不证明全部弱线索已核查。

事实使用 source_fact 或 risk_candidate 分类；源码差异与潜在业务后果分开。原有语法候选只用于提示，不升级为交易状态等业务事实。只有可能影响数据库、渠道、QCM、通知、退款状态或最终响应的未解析调用才生成必要关系义务；普通 DTO/枚举访问器、bean setter、builder 字段写入和字段映射构造不因绑定未解析而单独进入复核，由字段来源、分支与返回事实表达。只有关键状态读取、数据库查询、关键操作参数流或非访问器副作用继续形成关系义务。筛选依据是接收者、方法名、副作用和返回值是否流入关键写入/调用/状态分支，不扫描参数中的关键词。范围上限之外不生成预算边界或远距离缺口义务；达到限制的事实依据 `limits` 和相关变更源码 `hard_errors` 记录，不能将未扫描范围描述为已核实。

字段/常量变化包含初始化值和可确定消费者，始终生成 field_behavior 必要覆盖项；直接字段读取与注解访问器用于定位未修改的消费者。继承重载按有效签名和实参类型匹配；不确定类型不标为 source_resolved。switch 分支保留 case/default、分组标签与可能来源，穿透控制流保留显式边界。

`context.jsonl` 每行包含 id、project、side、tree、path、blob、start_line、end_line、digest、snippet。证据是对应树中文件的完整行片段；明显凭据做固定脱敏，校验时按相同方式重算。分析材料在本地留存，不用于对外暴露源码或敏感信息。

分析器 1.7.0 起，调用关系最多向上、向下扩展 2 层且每侧最多 100 个方法；移除仅凭同返回类型扩展调用图的逻辑。1.8.0 为提交时间线增加方法级行为候选摘要，并在配置消费者记录中加入读取位置、可识别入口、条件和直接使用语句。时间线以方法聚合，仅列 AST 行为投影发生变化的提交候选；报告先解释最终树行为，再针对相关方法核实候选的前后源码，忽略不改变外部行为的纯文本提交。配置消费者索引用于先集中定位每个入口的配置读取和使用点，再逐入口确认条件、用途与证据；“两层内未找到”不是全仓无消费者的证明。两类索引都须人工核对，不能替代源码证据。预算边界和远距离解析缺口不生成复核义务。未解析调用仅在本身命中关键副作用、状态或响应范围，或其值流入关键写入/调用/状态分支时进入复核；普通 DTO/枚举访问器、bean setter、builder 字段写入和参数关键词不会单独触发复核。相同绑定按接收者类型、停止原因、候选目标、方法名和参数个数共同复核，同时保留每个调用点和证据。旧分析材料不迁移，需重新采集。

## 用例覆盖关联

标准用例先按 [测试点契约](test-point-contract.md) 编译结构化目录，使用 schema_version=2、test_point_catalog 和 purpose_cases 四类数组；需求验收覆盖本次功能的正常流程，异常和边界单列。没有单独需求材料时，可登记 reviewed_change 来源，但每条关联规则必须引用本次固定 analysis 的事实和证据；归类不代表正式需求已确认或业务测试已执行。每条有 test_point_links 及以下 coverage_links。五列内容保持。单条用例的覆盖关联片段：

```json
{
  "case_id":"AC-001",
  "coverage_links":[{
    "obligation_id":"复制必要覆盖项的id",
    "fact_ids":["复制该项fact_ids"],
    "evidence_ids":["复制该项evidence_ids，可补充已核实证据"],
    "condition":{"expression":"按覆盖项原样填写","value":true},
    "assertion":{"kind":"按覆盖项原样填写","errors":["提取的明确错误结果"]},
    "observable_evidence_indices":[0]
  }]
}
```

condition/assertion 按覆盖项原样关联，不能自行换成另一个分支；数组位置从0开始，指向实际 observable_evidence。已提取的错误文本必须出现在该用例预期或所引用观察断言中。一个用例可关联多个确实覆盖的项目；不要求为每个语法提示单独建用例，也不能靠挂编号证明实际步骤已经完整覆盖。

按测试点契约，将可解析的源码触发条件与真实测试点谓词比较，并核对明确来源/错误断言及观察关联。仅复制 condition/assertion 元数据不能替代测试点条件。只接受当前四类用例与当前分析器/编译器版本，其他格式或版本直接拒绝。

## 补查与处置

review 文件结构：

```json
{
  "analysis_id":"对应本次analysis_id",
  "evidence":[],
  "dispositions":[{
    "obligation_id":"必要覆盖项id",
    "status":"reviewed_boundary",
    "review_kind":"model_source_review",
    "evidence_ids":["相关源码证据id"],
    "conclusion":"具体核实到的源码关系和停止位置",
    "limitations":"未能静态核实的业务或运行边界"
  }]
}
```

status 只允许 not_applicable（有证据说明不适用）或 reviewed_boundary（无法静态确定的关系、循环、动态查询、取证限制或历史边界）。已确定的行为不能用 reviewed_boundary 代替测试；不适用结论仍需要具体源码证据与说明。不要批量生成空洞豁免来消除覆盖缺口。

对绑定问题完全相同的多个必要关系义务，可在 `review.relation_batches` 中共同核验。规范签名要求同一方法、调用接收者、方法名、参数表达式、候选目标和 unresolved 原因；行号及分支 guards 不同仍逐成员保留证据与 obligation ID。每个成员必须有自己的原始证据，校验逐条展开结论，不会因为表达式相似就合并。

```json
{"status":"reviewed_boundary","review_kind":"model_source_review",
 "conclusion":"已核对各调用点，绑定候选和停止原因一致。",
 "limitations":"外部运行时实现仍未静态确认。",
 "members":[
   {"obligation_id":"关系义务1","evidence_ids":["证据1"]},
   {"obligation_id":"关系义务2","evidence_ids":["证据2"]}
 ]}
```

### 大量覆盖项的复核与推进

- 默认范围报告目标为 10 分钟内交付，包含源码采集/分析、复核、报告及可执行用例。10 分钟不是自动停止点：全量队列中的延后义务属于范围外统计，不使选定范围变成未完成；不得为清空队列而扩大范围。若所选工作实际超过 10 分钟，可在超过 10 分钟后提供一次标明缺口的阶段草稿，但继续完成最终范围报告和用例。只有真实障碍影响所选范围时，才以未完成报告结束。完整必要覆盖与完整校验属于用户要求正式全量阶段的标准。
- `review_workbench.py --analysis ... --output ... --fast10` 输出限额内的方法组、绑定组及必要成员追溯，不附带全量人工候选；快审阶段只按入选证据 ID 读取源码片段，不整份载入 analysis/context。完整分组视图仍可供正式全量阶段使用。默认只排最多 8 个优先方法组、4 个关系绑定组，每组最多抽查 3 个调用点，每个方法组最多 2 条非绑定义务。普通 getter/setter、Builder 属性调用、通用辅助调用及无关键数据流的返回不独立进入队列；预算边界和远距离解析缺口不生成逐项复核义务。
- 调用图只向上、向下扩展 2 层，每侧最多 100 个方法；无法索引变更源码、变更方法超限或关键变更证据因容量不足而缺失时，分析以 `hard_errors` 阻止完整交付。相同绑定组共同复核一次，所有成员的来源、表达式、义务 ID 和证据 ID 保留；若参数来源或适用条件不同，不能套用共同结论。
- 对每项依据源码判断是由可执行测试覆盖、确有证据证明不适用，还是存在无法静态确定的边界。相同关系可以共同阅读和归纳，但每项关联的结论、证据及适用范围都要真实匹配；禁止按数量、类型或校验错误批量套用未经核实的结论、伪造证据、测试步骤或预期。
- 快审优先检查影响关键数据、退款状态、渠道/QCM 副作用、通知和最终响应的未解析关系，使用同一固定快照核对绑定和来源。预算范围外不生成逐项缺口清单；报告如实列出调用深度和每侧方法上限，并区分静态分析与运行验证。
- 默认交付必须完成所选范围的业务流程、影响、配置前提和可执行测试用例，并单独导出四类工作表 Excel；报告列文件名及数量，不重复用例表格，标明范围及全量覆盖校验未执行。正式全量阶段才要求完成所有必要覆盖和完整校验。不得把未执行的构建、测试或渠道联调写成已完成。
- 维护一份滚动的规范测试点清单。每发现候选就先查现有身份；相同身份立即追加其来源、义务、事实、证据和数据组，语义等价只在源码证据支持时立即声明。先分批产生候选、再全量归并会重复计算，禁止这种两阶段做法。首轮登记完成后编译一次并做全量覆盖核对；后续仅修改新证据或校验错误所指向的条目，然后重新编译校验，不重建完整清单、不重并未受影响的用例。
- `review_workbench.py --analysis ... --catalog ... --output ...` 可从唯一测试点清单生成含固定关联的未完成用例骨架；新点应在登记时就关联到兼容用例，保持单一用例清单和逐项覆盖链。骨架的标题、前提、步骤、预期和观察描述必须人工填写，禁止将空内容或未经核实的生成内容作为完成结果。
- 真正阻塞包括源码或修订不可用、合成失败、权限或环境故障无法排除，以及关键业务预期无法从可用证据确定。先完成不依赖障碍的工作，交付标明未完成状态的报告并具体说明障碍及未完成项；不能通过更换修订、扩大范围或虚构处置绕过。

可在 evidence 中补充同格式源码片段，必须来自本次明确项目的 baseline/result 树；校验会重新读取 Git blob 核对。此处补充的是模型源码复核，不改变原关系状态，不声称脚本已解析。需求含义仍不明确时才向用户澄清，无需为普通静态边界逐项请求审批。

## 完成校验

范围报告校验检查章节、草稿标记、Excel 文件名及四类用例数量，并确认范围用例只引用快审入选的事实/义务；不要求清空范围外覆盖项。正式全量校验继续检查快照/版本身份、Git 文件归属与内容、事实和覆盖引用、测试点确定性重算及四类唯一归属、用例格式与去重后覆盖、例外证据、剩余必要覆盖项。Excel 导出失败不生成新的 Excel。

PASS 只说明静态证据和结构化覆盖声明可追溯、一致、无未处置项；不能证明模型写出的所有文字正确、动态调用绑定正确、用例确实执行或业务需求成立。报告必须继续区分静态分析、构建测试与真实联调。
