# diff-list

将明确指定的 Git 改动整理为测试人员能够据此编写用例的 UTF-8 Markdown。**只描述选中改动产生的最终净变化**，突出业务意义及风险，不写通用回归清单或源代码证据表。默认仅读仓库、写本地报告；**不修改业务代码、配置数据、数据库或 Git 状态，不自动提交**。

## 0. 运行要求与文件

- 环境：Windows 10、Git for Windows（`git` 在 PATH 中）、Python 3.8+（`py -3` 或 `python`）；脚本仅使用标准库。Windows PowerShell 5.1/7 均可调用。若工具缺失，应说明阻碍，不假装已经取证。
- 每次写报告前读取 `assets/diff-list-template.md`；模板**只能包含 Markdown 标题和空行**，不得写说明、示例或占位符。保持全部标题及顺序；没有关联变化的章节写“无”。
- 固定脚本：`scripts/repo_access.py` 自动缓存 GitHub 仓库；`scripts/collect_git.py` 只读提取确切提交与 diff；`scripts/impact_candidates.py` 在**指定修订**中检索候选引用；`scripts/init_report.py` 复制模板新建文档；`scripts/validate_report.py` 校验交付文档结构。用法见 `README.md`。
- `references/analysis-checklist.md` 为按需阅读的详细风险检查清单。脚本的候选和静态检查不是事实结论，调用链和业务预期必须核实源码、配置或已确认需求。

## 1. 输入、范围与只读边界

1. 必需：**GitHub 仓库 URL（或可从会话明确解析的项目名）及对应 Git 修订号**。用户只需在调用 Skill 时直接输入仓库与修订；**不要求配置 JSON 清单、提前克隆仓库或提供本机项目路径**。支持单提交、多个指定提交和显式 `base..head` 范围。不以当前 HEAD 替代缺失修订。多项目分别指定仓库与修订，名称无法唯一确定仓库时才询问 URL。
2. 可选：输出绝对路径、背景、重点业务、目标读者。默认目录 `G:\tmp`，缺失则创建，按时间生成不重名的具体 `.md` 文件；如果 G: 不可写，报告错误并请用户给出路径，不悄悄改位置。
3. 每个项目通过其 GitHub URL 在隔离缓存中自动 clone/fetch，缓存位置默认为 `%LOCALAPPDATA%\diff-list\git-cache`；读取缓存的真实 Git 根目录与状态。无需修改用户原有本地仓库，禁止 checkout/reset/cherry-pick 或执行 SQL。私有仓库依赖 Git for Windows 已配置的 GitHub 凭据，权限不足或网络失败时明确报告。
4. 修订不存在、合并提交父提交基线不明、不同分支选中提交不可比较，询问必要信息。合并提交明确选用哪一个父提交；范围须明确两个端点。不要将其他提交和工作树里的后续实现算进本次改动。
5. 使用 UTF-8，Windows 搜索优先 `rg`（如可用）。Git 结果优先按文件/关键词缩小读取规模。通常无需构建、启动服务、访问真实数据库；“验证情况”只报告**本次真的执行**的核对与未执行的验证。

## 2. 固定化取证及多提交最终归并

1. 根据用户在对话中指定的 GitHub 仓库和修订，按项目调用 `collect_git.py --repo <URL> --rev <SHA>`（多个提交重复 `--rev`，合并提交使用 `SHA:父节点序号`）或 `--base <修订> --head <修订>`；脚本自动准备隔离 Git 缓存，无需预先创建输入文件。它验证修订、父节点，收集 diff、文件清单和状态，对选中提交间**未选中提交修改同一路径**给出提醒。多项目分别调用，分析结果汇入**一份**提测 Markdown。证据 JSON 仅供内部分析，可能含敏感信息，**不得直接放入提测 Markdown**。
2. 单提交与其选定父提交比较；显式范围按 `base` 对 `head` 比较；多个离散提交分别取 diff，按提交祖先关系排列。若同一逻辑在本次多次修改，只保留最后生效结果。完全撤销、无净业务变化的不列。改动前行为取本次选择开始前的真实版本，而非中途版本。
3. **注意：脚本只检测文件级潜在交叉修改，不能自动证明最终业务归属。** 对涉及同一方法、字段、配置键或间接依赖的未选中提交，继续做人工精确归属；无法独立确认时在对话中询问，不用“最早提交到 HEAD”大范围 diff 代替选中集合。
4. 提交非当前 HEAD 时，后续阅读代码使用 `git show <完整SHA>:<仓库相对路径>`、`git grep <SHA>` 等指定修订内容；工作树仅辅助定位。不要凭注释、提交摘要或记忆推断可执行行为。合并、重命名、revert、cherry-pick 注意重复和净效果。
5. 需要的信息不足时，先完成不依赖该问题的分析，影响结论/配置/预期的问题在对话中确认，不在 Markdown 中留“待确认”事项。

## 3. 业务影响追踪（新增，重点）

对**本次实际改变行为**的入口、方法、字段、枚举、消息、表字段和配置键，按必要范围进行**双向分析**：

- **向下**：入参校验 → 条件分支 → 参数映射 → Dubbo/HTTP/MQ/定时任务 → 数据库、Redis、状态落库 → 外部通知、查询、超时与补偿。明确成功、失败、未知和重试路径。
- **向上**：找出调用该方法/契约/配置的接口、消费者、定时任务和跨服务入口，包括**本次没有改动源码**的调用方。`impact_candidates.py --symbol` 只列字面引用候选，不支持精确 Java 类型绑定；需继续核实调用目标、动态派发、反射、路由和实际使用条件。
- 发现公共工具、状态枚举、Mapper、配置默认值修改时优先追踪其消费者；仅纳入与选中改动存在实际影响关系的流程，不做无关的全项目审查。
- 区分“本次新增/调整”和“沿用的既有行为”。静态无法证明动态路由或运行时配置结果时，不宣称已经确认。跨项目用项目名说明调用方向及责任边界。

## 4. 需求行为、实际行为与缺陷（新增）

在内部分析中为每项重要行为区分：**改动前行为 / 指定修订的实际行为 / 已确认需求或验收预期 / 依据充分度**。只有代码和需求一致时，才把该结果直接表述为验收预期。

- 如需求明确、代码违背需求：向用户说明差异；文档“特殊逻辑”写清**当前实际表现及影响**；重点测试写**已确认的正确验收目标**，明确当前实现不能满足，不将 Bug 当成正确预期。
- 如需求未说明、代码表现反常：不要自行判错或编造理想预期；就影响结论的关键冲突在对话中询问。分析证据不充分时只写能证实的事实，不作强结论。
- 注释与代码矛盾时以执行代码为当前行为，写明注释差异；注释掉的调用不能当成已启用功能。
- 不因本次发现问题自动修业务代码，不自动运行修复 SQL 或改变任何环境配置。

## 5. 改动清单的填充规则

### 5.1 需求改动

按业务功能/入口描述触发条件、最终结果、影响范围、跨项目职责与调用方向；不是把 Java 类或文件名逐条翻译。报告始终明确四类结论：**需求改动、表字段 DDL、表配置 DML 准备、配置文件调整**是否涉及。

### 5.2 表字段 DDL 修改

真正有结构改动时列系统、表、字段/索引、改动前后定义及相关默认值/NULL 约束，列已核实 DDL 脚本仓库相对路径与所属修订；新表说明作用。代码需要新字段但找不到配套脚本，写“代码涉及新增字段，DDL 脚本未找到”。复用旧表旧列及新增 Redis key 不算 DDL。无变化写“无”，不编造可执行 SQL。

### 5.3 表配置 DML 准备清单

这是**测试前应具备的配置事实**，不判断现有环境究竟需要 INSERT/UPDATE。建议列：`系统/表`、`字段（配置键）`、`字段状态`、`配置含义或取值`、`作用范围及测试前提`。

- `字段状态` 相对于本次改动前的**该系统/表/作用域中的配置键**而言：新支持的键/作用域标“新增”，原已支持且沿用的标“已存在”；不代表数据库物理字段或测试环境中已存在一行记录。同键跨表或作用域须分别列；同一行混合状态须拆行。无法证实先询问。
- 不设置“是否必须新增数据”列，不写“已有数据则无需新增”。`param_name`/`param_value` 等物理列即使旧有，也不能让新增配置键误标“已存在”。
- **新增检查删除/废弃场景**：配置键不再被读取、作用域被移除、值语义或默认值改变时，明确写其“废弃/删除/变更”的实际影响；这不等同要求删除数据库记录。保留常规行中的“新增/已存在”定义；废弃项另用文字或单独表说明，不能冒充字段状态。
- 区分“仓库是否交付 DML 脚本”与“测试前需要的配置”；未交付 SQL 不等于无需配置。表配置值须按所属系统真实枚举和分支核验，不能跨服务套用；密钥、公钥只写配置位置、用途，不写真值。若新增配置只补 DML 还不足以生效，要说明必要代码分支/开关。
- 不从静态代码断言测试库/生产库中数据确实存在或已经生效。

### 5.4 配置文件调整

- 环境 properties 文件统一概括为 **`profile/*.properties 配置文件`**，不展开每个 dev/uat/pre 文件，也不罗列没变更的文件。实际是 YAML、XML、环境变量等，写真实格式及仓库相对范围，不虚构 profile 目录。
- 逐项标记新增、修改、删除、废弃的键，以及取值意义、默认值、覆盖优先级和测试/生产环境差异（均以代码为准）。沿用的旧配置单独标“沿用”；引用新键却没有配置值时明确指出缺失，不视为无改动。
- 有文件变化时提供实际格式的**配置片段**，只保留相关键与必要层级。删除项可在示例旁说明删除前的键及删除后是否有替代配置。示例不能编造取值、泄露敏感值；环境相关内容注明示例/占位。
- 无调整写“无”。

## 6. 业务流程、特殊逻辑与测试风险（新增）

- 业务流程按测试视角描述：输入、校验、路由、渠道交互、状态、订单号、金额单位、时间、通知、缓存与异常恢复。图文一致，必须使用 **Mermaid 8.8.3** 能兼容的 `flowchart TD` 或 `sequenceDiagram`；失败分支不能画成必然成功。没有任何相关流程变化时对应章节可填“无”。
- 特殊逻辑只提本次有业务价值的条件、分支替换、渠道例外、绕过、未启用、开关及异常。每个点交代触发条件、当前结果、与类似流程的差别及关注点；不要给出源码位置、行号或证据编号。
- 重点核验：延迟调用与重复请求的区别、幂等、重试订单号复用、并发锁、渠道与本地状态不一致、未知交易结果、超时边界、状态通知和回补；协议字段长度/上限只有核实后才写具体值。确定越界时写清触发条件，不含糊描述为“联调看看”。
- **内部风险筛选**：按 `references/analysis-checklist.md` 逐项考虑条件分支、状态流转、并发幂等、金额精度、时间边界、数据一致性、异常恢复和兼容性，只输出与**本次变化**有关且有明确验证价值的高/中风险场景。不凑数量，不把通用部署检查与正常接口全列出来。
- “特殊逻辑与测试关注点”负责解释行为差异，“重点测试场景”负责可执行的操作、前提和可观测结果，不重复长篇背景。

## 7. 重点测试场景的固定格式

每个场景按下面三个标签分行，必要时编号，不写覆盖全接口的长表：

**测试点：** 要执行的业务操作和针对的风险。

**测试前提：** 与场景有关、已核实的配置键与取值、状态、渠道真实结果、时间与重复条件；不复制整个环境清单，不编造状态编号。

**预期结果：** 可观察并判定的本地/渠道状态、金额、订单号、字段来源、通知或错误；不得只写“成功/正常”。如当前代码违背已确认需求，明确其不能满足该预期（参见第 4 节）。

没有独特风险场景时，章节写“无”。对普通查询、退款等既有路径只在流程中简述，不自动展开全面回归。

## 8. 输出、自动检查和交付

1. 运行 `init_report.py` 用模板新建文档，**不要改模板标题**；把所有项目和各自**完整 40 位 Git SHA**写在“分析范围”。DDL/DML 脚本或配置位置只能使用仓库相对路径。报告不依赖本地盘符与源码链接。
2. 文档不输出“代码依据”章节、表、列、编号、源码行号，也不输出“待确认/待核实”或其他未决问题；有影响的问题**提前在对话中确认**。未访问真实环境是验证边界，不是待用户答复事项。
3. 运行 `validate_report.py`（可用 `--expect 项目名=完整SHA` 多次）执行标题顺序、四类内容、Mermaid 围栏、测试标签、敏感路径、禁用词和 UTF-8 检查，修正失败项。它**不解析 Mermaid 8.8.3 全语法**，还需人工检查图文一致及必要时用相应渲染器验证。脚本不能证明动态执行或业务正确。
4. 再人工检查：选中提交隔离与最终净效果、未选中提交交叉、双向影响范围、DDL/DML/配置删除场景、需求与实际行为冲突、测试结果可判定、真实验证范围。无相关变化的章节写“无”。
5. 确认文件确已落盘、UTF-8 中文正常，不覆盖无关文件。最终简短回复**本地绝对路径**、覆盖项目/修订和本次实际验证方式；如果执行环境能提供文件链接则附链接，不把本机 Windows 路径伪装成网页下载链接。
